atomicity guard — standalone unit-level runs for patch 0001
===========================================================

WHY THIS FILE EXISTS
  `concurrent_burst_admits_exactly_one_request` is classified as a GUARD in the
  patch header and README. The server-level bursts that exist for both builds
  are identical (1 served / 63 rejected — docs/re/evidence/c0-burst.tsv for the
  unpatched binary, c1-burst.tsv for the patched one), so they cannot show what
  the pre-patch read-then-write shape does wrong. These runs isolate the
  primitive: both `check_and_increment` bodies verbatim, in-process, against the
  lockfile's moka, at the three optimisation levels that matter.

MODE `deterministic` — no threads, no timing, no optimisation sensitivity
  The two halves of the old pair are interleaved by hand: A reads, B reads
  (A has not written yet), A writes and decides, B writes and decides. This is a
  legal execution of the pre-0001 code path; it proves the shape is non-atomic
  without depending on scheduling.

  opt dev  original  interleaved reads (A=1, B=1) -> served=2 of budget 1: A_ok=true B_ok=true
  opt dev  patched   same two requests, one call each -> Ok(1) then Err(()) (budget 1)
  opt opt1 original  interleaved reads (A=1, B=1) -> served=2 of budget 1: A_ok=true B_ok=true
  opt opt1 patched   same two requests, one call each -> Ok(1) then Err(()) (budget 1)
  opt opt3 original  interleaved reads (A=1, B=1) -> served=2 of budget 1: A_ok=true B_ok=true
  opt opt3 patched   same two requests, one call each -> Ok(1) then Err(()) (budget 1)

MODE `burst` — the test's own scenario: 64 threads released from one barrier,
  10 trials per configuration. The harness iterates FOUR configurations per
  invocation (patched/original x budget 1/8); with the three opt-levels above
  that is 12 configurations x 10 trials per run, SIX of them patched.
  `overshoot_trials` counts trials that served more than the budget.

READING (measured, not inferred)
  * The upsert shape served EXACTLY its budget in all of its configurations:
    SIX per run (patched x budget 1/8 x opt 0/1/3), 10 trials each, i.e. 12
    patched configurations across runs A+B, 0 overshoot trials — the invariant
    the guard asserts holds.
  * The pre-patch shape overshoots, but only sometimes: 0/10 to 8/10 trials
    depending on opt-level AND ambient load, and the ordering by opt-level
    REVERSES between runs A and B (opt-3 gave 6/10 in A and 0/10 in B at budget
    1). From the code alone the outcome is not reproducible — arrival spread on a
    4-vCPU host is the controlling variable, which is also why the server-level
    burst (requests spread over ~400 ms) shows nothing at all.
  * The non-atomicity itself is NOT stochastic: the deterministic interleaving
    serves 2 on a budget of 1 at every opt-level, and the upsert shape answers
    Ok(1) then Err(()) for the same two requests.
  * Consequence for the build side's 3 clean runs of the repo `#[test]` on the
    v0.10.0 arm: entirely consistent with the measured per-trial overshoot rate
    at the repo's opt-1 (1/10 to 3/10 here) — three clean runs have probability
    ~0.3–0.7. A pass on the v0.10.0 arm therefore does not contradict these
    numbers, and neither does a failure.

STATUS
  The guard stays a guard: a FLAKY detector of a real, deterministic-in-shape
  defect. It is not counted in any RED column, and the atomicity half of patch
  0001 is pinned at the level of the argument (shape + deterministic
  interleaving), not demonstrated by a test that fails reproducibly.
  Next variable to control, if a reproducible gate is wanted: arrival spread
  (start the 64 threads in controlled waves, or measure on an idle machine with
  the compiler stopped) — not the optimisation level, which alone reverses order
  between runs.
